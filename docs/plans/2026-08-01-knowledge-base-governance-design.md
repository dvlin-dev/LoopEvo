# LoopEvo 知识库治理设计

## 目标

为 LoopEvo 建立一套面向开源项目和 AI Agent 协作的仓库级知识库规范，使人和不同 Agent 能够从同一入口理解项目身份、事实边界、当前约束和文档位置，同时避免重复维护、过程信息长期残留以及规划能力被误写为已实现能力。

本次工作只建设文档治理基线，不提前规定尚未确定的运行时语言、框架、数据库、部署平台或 UI 工程规范。

## 当前问题

仓库当前已有完整的中英文 README、产品架构设计和仓库初始化计划，但尚未建立统一的协作入口与知识生命周期：

- 没有仓库级 `CLAUDE.md` 与兼容 agents.md 规范的 `AGENTS.md`；
- `docs/superpowers/specs` 与 `docs/superpowers/plans` 不符合目标目录结构；
- 产品架构设计使用英文，不符合内部知识库统一使用中文的约束；
- 已完成的初始化计划仍与稳定设计并列，容易让执行历史被误认为当前事实；
- 尚未定义事实、计划、原型、验证证据和历史记录之间的权威关系；
- 尚未定义第三方数据、浏览器操作、密钥、生成代码和工作流进化的长期安全边界。

## 设计原则

1. **单一入口。** 每个作用域只维护一个真实入口文件，兼容文件通过相对符号链接指向它。
2. **稳定事实优先。** 长期文档只描述当前有效事实、约束和验证基线，不记录执行流水账。
3. **计划与事实分离。** 未采纳或未落地的方案留在 `docs/plans`，不能提前进入功能事实文档。
4. **原型不等于实现。** HTML 和静态原型只能表达方向，不能作为产品或代码事实源。
5. **历史交给 Git。** 不建立 `archive` 目录；过时内容删除前先回写仍然有效的事实。
6. **按需建设规范。** 技术栈和模块出现后再增加对应规范，避免为尚不存在的系统过度设计。
7. **证据约束结论。** 文档必须区分已验证事实、已采纳设计、执行中计划和未验证判断。
8. **治理同样适用于 Agent。** Agent 不因能够自动编排、操作浏览器或生成代码而绕过权限、评审、测试和发布边界。

## 入口与权威关系

### 仓库级入口

根目录 `CLAUDE.md` 是仓库级协作入口，只记录：

- LoopEvo 的稳定身份、目标和当前阶段；
- 不可突破的产品、数据与协作边界；
- 文档分类及阅读路由；
- 开始任务、修改文件、验证和交付时必须遵守的通用规则。

根目录 `AGENTS.md` 必须是指向 `CLAUDE.md` 的相对符号链接。不得把它复制成普通文件，也不得同时维护两套内容。

### docs 级入口

`docs/CLAUDE.md` 是 `docs/` 的唯一导航与治理入口，负责定义目录职责、文档生命周期、元数据要求和查找方式。`docs/AGENTS.md` 必须是指向同目录 `CLAUDE.md` 的相对符号链接。

`docs/CLAUDE.md` 不维护容易过期的完整文件清单，只维护目录级路由和少量必须阅读的核心事实源。

### 冲突处理

文档出现冲突时，按以下顺序处理：

1. 当前代码、测试、配置和可重复验证结果；
2. `CLAUDE.md` 中的仓库级硬约束；
3. `docs/design` 与 `docs/reference` 中状态为 `active` 的稳定事实；
4. `docs/plans` 中执行中的设计和计划；
5. `docs/prototype` 中的方向性表达；
6. Git 历史、Issue、讨论和聊天记录中的历史信息。

发现冲突时不能静默选择对自己方便的结论。应验证当前实现，修正文档，或明确记录尚未验证的缺口。

## 目录职责

### `docs/design/core`

存放已经采纳、需要跨功能长期维护的产品和架构事实，例如产品边界、核心生命周期、工作流模型、能力层、治理模型和系统分层。

这里可以记录尚未全部实现但已经作为项目长期约束采纳的架构设计，必须明确标注当前实现状态，不能把目标架构写成现状。

### `docs/design/features`

只存放已经落地功能的稳定设计事实，包括用户行为、模块边界、数据流、错误处理和已验证限制。未实现功能、候选方案和执行计划不得进入此目录。

### `docs/plans`

存放新需求的设计说明、实施计划和执行期评审文档。它是工作区，不是长期事实库。

计划完成后的处理顺序：

1. 根据代码和验证结果确认最终实现；
2. 把仍然有效的事实回写到 `docs/design` 或 `docs/reference`；
3. 修正受影响的入口和路由；
4. 删除已完成的过程文档；
5. 使用 Git、提交记录和 PR 保存历史。

### `docs/prototype`

只存放 HTML、静态原型及运行原型所必需的本地资源。每个原型必须显著声明“仅表达方向，不是实现事实源”，并链接到对应的执行中设计文档。

### `docs/reference`

存放不依赖某个功能、可跨任务复用的稳定工程规则，包括仓库上下文、协作交付、验证策略、安全与数据治理。该目录保持扁平，只有出现大量同类且长期维护的文档时才允许增加子目录。

## 文档语言与格式

- 根 `README.md` 继续作为英文开源首页，`README.zh-CN.md` 是完整中文镜像。
- `CLAUDE.md` 以及 `docs/` 下的知识库正文统一使用中文。
- 文件名使用简短、稳定的英文 kebab-case，正文标题使用中文。
- 技术名称、协议名、代码符号和平台品牌保留官方写法，不强行翻译。
- 稳定文档统一使用以下 Front Matter：

```yaml
---
title: 中文标题
scope: repository
status: active
---
```

- `scope` 表示规则适用范围，使用稳定目录名、模块名或 `repository`。
- `status` 只允许 `draft`、`active`、`in_progress`、`completed`。
- 不使用手工维护的“最后更新时间”冒充新鲜度，变更时间通过 Git 获取。
- 不复制大段代码或外部文档；优先记录契约、入口、约束、验证方法和权威链接。

## 稳定参考文档

### 仓库上下文

`docs/reference/repository-context.md` 记录项目定位、当前阶段、已经存在的仓库资产、尚未确定的技术决策和关键阅读入口。它不能把路线图目标写成已经实现的系统。

### 协作与交付

`docs/reference/collaboration-and-delivery.md` 记录任务边界、先调研后修改、最小变更、用户修改保护、外部反馈验证、提交授权、事实回写和交付证据要求。

### 测试与验证

`docs/reference/testing-and-validation.md` 采用风险分级而不是固定执行全量构建：

- L0：纯文档和静态原型，检查路径、链接、软链、格式和渲染；
- L1：局部逻辑、连接器、工作流定义或 UI，运行目标测试和相关静态检查；
- L2：权限、密钥、第三方数据、调度、执行引擎、状态迁移或发布配置，增加集成测试、安全检查和失败/回滚路径验证。

在技术栈确定前只定义验证原则，不编造不存在的命令。

### 安全与数据治理

`docs/reference/security-and-data-governance.md` 记录以下长期边界：

- 第三方平台数据必须通过官方 API、明确授权、有效合同或符合条款的访问方式获取；
- 连接器必须暴露权限、成本、配额、数据范围和删除约束；
- 密钥只通过受控秘密管理注入，禁止进入代码、日志、证据和文档；
- 浏览器操作遵循最小权限，不执行未经授权的不可逆外部动作；
- Coding Agent 生成的模块必须经过与人工代码相同的评审、测试、沙箱和发布控制；
- 工作流进化只能提出可版本化变更，必须保留证据、审批策略、灰度与回滚路径；
- 用户数据、个人信息和受许可数据必须具备来源、保留、访问和删除边界。

1. 根目录和 `docs/` 内的 `AGENTS.md` 都是有效的相对符号链接，且分别解析到对应 `CLAUDE.md`；

6. 所有 Markdown 相对链接指向存在的文件，文档路由与实际结构一致；
7. 安全规则覆盖第三方数据、密钥、浏览器操作、生成代码和受治理进化；

9. 远端默认分支回读后，软链类型、核心文档和提交内容与本地一致。
