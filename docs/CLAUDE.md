# docs/ 知识库指南

## 目录职责

- `docs/CLAUDE.md`：知识库唯一导航与治理入口；不新增 `docs/index.md`。
- `docs/AGENTS.md`：指向同目录 `CLAUDE.md` 的相对符号链接，用于兼容 agents.md 规范。
- `docs/design/core/*`：已经采纳、需要跨功能长期维护的产品和核心架构事实。
- `docs/design/features/*`：已经落地功能的稳定行为、边界、数据流和已验证限制。
- `docs/reference/*`：跨任务复用的工程规范、协作规则、验证流程和安全约束。
- `docs/plans/*`：新需求设计、实施计划和执行期评审文档；属于临时工作区。
- `docs/prototype/*`：HTML、静态原型及必要资源；只表达方向，不是实现事实源。

Git 不保存空目录。没有有效内容时，不使用 `.gitkeep`、占位 README 或空模板强制创建目录。

## 文档权威顺序

出现冲突时，按以下顺序验证和处理：

1. 当前代码、测试、配置和可重复的真实验证结果；
2. 根目录 `CLAUDE.md` 中的仓库级硬边界；
3. `docs/design` 与 `docs/reference` 中状态为 `active` 的稳定事实；
4. `docs/plans` 中执行中的设计与计划；
5. `docs/prototype` 中的方向性表达；
6. Git 历史、Issue、PR、讨论和聊天记录中的历史信息。

高优先级内容不代表永远正确。发现实现、文档和目标设计不一致时，应明确它们分别代表“当前现状”还是“已采纳目标”，验证影响后更新事实源，不得静默忽略冲突。

## 内容路由

| 要记录的内容 | 目标位置 |
| --- | --- |
| 项目身份、硬边界、协作入口 | 根 `CLAUDE.md` |
| 当前仓库资产、技术状态和阅读入口 | `docs/reference/repository-context.md` |
| 跨功能长期产品或架构决策 | `docs/design/core/*` |
| 已经落地功能的稳定事实 | `docs/design/features/*` |
| 新需求候选方案、设计与实施步骤 | `docs/plans/*` |
| 跨任务工程规则和验证方法 | `docs/reference/*` |
| 可视方向、HTML 和静态交互探索 | `docs/prototype/*` |
| 历史过程、旧版本和执行播报 | Git、Issue 或 PR |

如果一份文档同时承担计划和稳定事实，应先拆清当前状态；不要通过增加副本解决边界不清。

## 文档生命周期

### 新需求

1. 调研当前代码、事实源和外部约束。
2. 将候选方案与已确认设计写入 `docs/plans`。
3. 设计获得确认后编写实施计划，并在执行期间记录必要的评审结论。
4. 代码完成后依据实现和验证证据整理最终事实。
5. 将稳定内容回写到 `docs/design` 或 `docs/reference`。
6. 更新受影响的入口与相对链接。
7. 删除完成的计划和过程文档，历史交由 Git 保存。

### 稳定文档变更

- 仅保留当前有效结论、契约、入口、约束和验证基线。
- 删除时间线、逐轮讨论、临时负责人和已经失效的任务状态。
- 行为或架构变化时，在同一交付中同步修改对应事实源。
- 删除文档前，先确认仍然有效的事实已迁移且引用已更新。
- 同一主题优先维护一个事实源；只有“摘要入口”和“详细正文”承担不同抽象层级时才允许并存。

## 状态与 Front Matter

知识库 Markdown 使用以下 Front Matter：

```yaml
---
title: 中文标题
scope: repository
status: active
---
```

- `title`：清晰、稳定的中文标题。
- `scope`：规则适用范围，使用 `repository`、稳定目录名或模块名。
- `status`：只允许 `draft`、`active`、`in_progress`、`completed`。

状态含义：

- `draft`：尚未采纳的候选内容，不能作为实现依据。
- `active`：当前有效的稳定事实或已采纳约束。
- `in_progress`：正在执行的设计、计划或评审文档。
- `completed`：仅用于尚未完成事实回写和清理的短暂阶段；完成清理后不保留过程文档。

不手工维护“最后更新时间”。内容新鲜度通过 Git 历史和当前实现验证，不通过容易失真的日期字段判断。

## 语言与命名

- 根 `README.md` 是英文开源首页，`README.zh-CN.md` 是完整中文镜像。
- 根 `CLAUDE.md` 以及 `docs/` 下知识库正文使用中文。
- 文件名使用简短、稳定的英文 kebab-case。
- 技术名称、协议、平台品牌、代码符号、命令和路径保留官方写法。
- 避免无解释的缩写、宣传性表述和无法验证的绝对结论。
- 目标能力使用“计划”“应当”“目标是”等措辞；只有实现和验证证据充分时才使用“已支持”“当前行为”。

## 结构约束

- `docs/` 第一层只允许 `CLAUDE.md`、`AGENTS.md`、`design/`、`plans/`、`prototype/`、`reference/`。
- `docs/design` 默认按 `core/` 与 `features/` 分类；只有产生长期维护的运行手册时才评估增加 `runbooks/`。
- `docs/reference` 保持扁平；不要为少量文件增加深层目录。
- `docs/plans` 与 `docs/prototype` 不能反向成为稳定事实源。
- 禁止新增 `archive/`、重复入口、生成产物或外部文档整份副本。

## 查找与维护

先查看实际结构，再按主题搜索：

```bash
rg --files docs | sort
rg -n "关键词" docs
```

修改文档路径后必须搜索旧引用：

```bash
rg -n "旧路径" CLAUDE.md README.md README.zh-CN.md docs
```

完成文档修改后，按 `docs/reference/testing-and-validation.md` 执行最小充分验证。文档验证通过只证明结构与格式满足要求，不自动证明业务内容仍然新鲜；事实仍需通过代码、测试、授权数据源或真实环境确认。
