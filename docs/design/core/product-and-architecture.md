# 产品定义与核心模型

## 文档定位

本文是 LoopEvo 的产品事实源，回答“为谁解决什么问题、产品是什么、核心对象如何协作、什么不做”。技术实现见 `system-architecture.md`，界面规范见 `ui-design-system.md`，当前执行顺序见 `../../plans/roadmap.md`。

本文描述的是 **已采纳的产品方向**。仓库仍处于 Pre-alpha / 设计阶段，除“当前状态”明确列出的文档资产外，本文能力尚未实现。

## 一句话定位

> LoopEvo 是一个开源的目标到工作流平台：用户用自然语言描述持续目标，系统将其编译成可审查、可恢复、可验证、可版本化演进的长期 AI 工作流。

它解决的不是“Agent 能否临时完成一次任务”，而是：如何把有效方法沉淀为能长期运行、保留证据、控制成本、接受反馈并安全改进的产品资产。

```text
目标
→ 调研问题与信源
→ 提出工作流
→ 审批并发布版本
→ 持久执行
→ 保留证据与结果
→ 评估质量、成本与风险
→ 提出变更
→ 回放、审批、灰度或回滚
```

## 核心问题

现有工具通常只覆盖闭环的一部分：

| 产品形态 | 擅长 | 常见缺口 |
| --- | --- | --- |
| 对话 Agent | 当前会话中的开放推理 | 有效过程随对话消失，难以长期运行和审计 |
| 自动化平台 | 稳定重复执行，并逐步支持 AI 生成与编辑流程 | 信源策略、原始证据、固定版本 Run 和治理发布链仍是各产品自定义能力 |
| Agent 框架 | 为开发者提供模型和工具循环 | 产品状态、权限、证据、评估与发布治理需要另建 |
| 垂直情报产品 | 提供特定领域的数据和分析 | 数据源、方法和流程难以迁移到其他目标 |

LoopEvo 聚焦缺失的一层：**从目标发现工作流，并让工作流成为可持续验证和演进的长期资产。**

## 目标用户

### Phase 1 首要用户

小型软件 / AI 产品团队中负责竞争与用户情报的产品或增长负责人。他们是实际操作者，能判断信号是否有用，拥有或能获得数据源预算与账号授权，但不希望先学习 API、抓取器、Cron、Agent 框架和流程画布。

他们希望：

- 直接说明“我想长期知道什么”或“我想重复完成什么”；
- 看懂系统准备使用哪些来源、能力、频率、权限和预算；
- 在授权后持续收到有证据的结果，而不是反复手工搜索；
- 能指出噪声、漏报和错误，让工作流在受控条件下改进。

技术创始人或工程负责人是部署、Provider 与安全决策者；首版不要求他们参与日常工作流操作。

### 扩展用户

- 研究人员和运营团队：将同一闭环用于研究雷达与重复运营任务；
- 团队管理员：管理共享工作流、凭据、预算、审批和数据边界；
- 开发者与开源贡献者：开发 Connector、Skill、MCP Adapter、评估器和交付渠道；
- 平台团队：自托管核心能力，并接入企业身份、秘密管理、通知和审计系统。

MVP 只以首要操作者的主题情报任务验证价值，不提前为扩展用户建设完整企业权限矩阵或公共市场。

## 核心用户任务

1. **表达目标：** 用自然语言描述主题、期望结果、范围、周期、预算和不可触碰的边界。
2. **审查方案：** 查看系统发现的对象、信源、采集方法、能力依赖、覆盖缺口与成本估算。
3. **连接能力：** 仅对被接受的来源授予最小必要权限或配置合法 Provider。
4. **运行与接收：** 手动、定时或事件触发工作流，并在 Web、Webhook 或通知渠道接收结果。
5. **验证结论：** 从摘要回到原始证据，了解来源、时间、处理链路和不确定性。
6. **反馈与改进：** 标记有用、噪声、漏报或错误，审查系统提出的版本 Diff，再决定是否发布。

## 产品形态

### 主要入口：Web 应用

Web 应用采用“对话控制面 + 持久事实面”：

- **对话** 用于表达目标、解释计划、请求授权和提出变更；
- **Workflow** 展示当前版本、步骤、来源、触发器、策略与预算；
- **Run** 展示一次执行的状态、重试、成本和步骤结果；
- **Evidence** 展示原始证据、引用、内容哈希和派生关系；
- **Evaluation** 展示质量、反馈、回放和版本对比；
- **Approval** 承载权限、发布、灰度和高影响动作的确认。

对话不是事实源，空白拖拽画布也不是默认入口。流程图用于解释和审查已经生成的工作流。

### 补充入口

- API / Webhook：创建运行、读取结果和接入外部系统；
- 通知 Adapter：邮件、通用 Webhook，以及公司版本的如流等渠道；
- CLI：面向开发、调试、自托管和扩展开发，晚于 Web 垂直切片交付。

开源核心不绑定公司内部渠道；公司专用逻辑通过独立 Adapter 接入。

### 开源与部署模型

- 仓库核心使用 Apache License 2.0，自托管必须是一等使用方式；
- 用户可 BYOK 接入模型、搜索、社交数据和通知 Provider，费用与授权关系保持透明；
- 未来可以提供托管服务，但核心 Workflow、Run、Evidence 和导出能力不得依赖托管专有格式；
- 公司版可以拥有私有 Connector、Policy 和 Delivery Adapter，但必须遵循相同契约，避免 Fork 核心运行时；
- 具体商业化、托管范围和企业功能尚未决策，不在设计阶段虚构价格或版本权益。

## 核心领域对象

| 对象 | 责任 | 不承担 |
| --- | --- | --- |
| `Project` | 一个长期目标及其上下文、成员和默认策略 | 具体执行状态 |
| `SourceStrategyVersion` | 不可变的候选信源、选择理由、查询方式、覆盖、授权、费用和缺口 | 原始采集内容 |
| `Source` | 信源、访问方式、可信度、覆盖、成本和许可信息 | 把外部内容当可信指令 |
| `Capability` | 带版本、输入输出、权限、成本和失败模型的可执行能力 | 产品工作流状态 |
| `WorkflowVersion` | 不可变的触发器、步骤、能力版本、策略、预算和评估规则 | 运行时被原地修改 |
| `Release` | 当前启用、候选、灰度和回滚版本的发布关系 | 保存对话上下文 |
| `Run` | 一次可恢复、可审计且固定版本的执行 | 作为新版本设计稿 |
| `Evidence` | 原始内容、规范化信息、引用、时间和派生链 | 未注明来源的模型结论 |
| `Evaluation` | 质量、时效、覆盖、噪声、可靠性、成本和反馈 | 直接发布变更 |
| `EvolutionProposal` | 变更 Diff、依据、风险、回放结果和发布建议 | 静默改写生产版本 |
| `ApprovalRequest / Decision` | 记录动作、范围、风险、费用、请求者、决策者、有效期和结果 | 替代实际权限控制或沙箱 |
| `Memory` | 有作用域、来源、时效和冲突状态的用户偏好或项目知识 | Workflow、Policy 或授权规则 |
| `CredentialReference` | 指向外部秘密管理系统的受控引用 | 存放明文密钥 |

Pi Session 是 Agent 的推理上下文，不等于 `WorkflowVersion` 或 `Run`；聊天记忆、用户偏好、主题知识、信源检查点和工作流定义必须分别治理。

## 产品闭环

### 1. Intent：定义结果

系统提取目标、对象、范围、周期、输出、预算、成功标准和禁止事项。缺失信息优先通过调研和低风险默认值补全；会改变数据授权、成本或结果方向的事项必须请求确认。

### 2. Discover：调研链路

Agent 调研候选对象、信源、API、RSS、网页、连接器和交付渠道，并为每项记录选择理由、授权方式、成本、覆盖和风险。首次调研结果沉淀为新的 `SourceStrategyVersion`，而不是留在聊天记录里或原地覆盖旧版本。

### 3. Compile：形成版本

确定性编译器将接受的方案校验并生成 `WorkflowVersion`。它固定触发器、步骤、能力版本、输入输出、超时、重试、checkpoint、预算、权限和评估规则。

### 4. Execute：持久执行

工作流按事件、Webhook、Schedule 或手动请求运行。系统保存状态和检查点，保证幂等、去重、限流、失败恢复、停止和人工等待。

### 5. Evaluate：验证结果

结果以证据而非模型置信度为中心。评估结合确定性检查、离线数据集、模型评估和用户反馈，衡量有用性、准确性、覆盖、时效、噪声、可靠性、延迟和成本。

### 6. Evolve：受治理地改进

系统从失败、反馈、成本和环境变化中提出最小变更，形成独立 `EvolutionProposal`。候选版本通过静态校验、历史回放、离线评估、预算与安全检查后，才能进入人工审批、灰度和晋升；退化时停止或回滚。

## 产品原则

1. **Intent first, graph second：** 用户从结果开始，系统负责解释生成的图。
2. **Workflow is the product：** 真正资产是版本化工作流，不是聊天记录或 Prompt。
3. **Evidence before confidence：** 结论、动作和改进都能回到来源、运行和评估。
4. **Deterministic by default：** 抓取、检查点、去重、重试、预算、权限和通知优先使用普通代码；Agent 只处理需要判断的部分。
5. **Governed evolution：** Agent 可以提出变更，不能直接修改线上流程、能力或代码。
6. **Least capability：** 每次运行只获得当前版本声明的最小能力、数据和网络范围。
7. **Cost is observable：** 新鲜度、覆盖、质量、延迟和费用共同优化，不用固定高频轮询掩盖设计问题。
8. **Open-source core, portable contracts：** 核心模型不绑定模型、社交数据、调度或托管供应商。
9. **Vertical slice before platform breadth：** 用真实端到端场景验证核心，再扩展抽象和生态。

## 首个垂直切片：主题情报

用户可以描述：

> 持续跟踪 medo.dev、同类 AI 建站产品及其用户讨论；发现产品发布、设计趋势、功能诉求和抱怨；每天生成有引用的简报，高优先级信号即时通知。

工作流应当：

1. 识别品牌、竞品、品类词、社区、账号和权威站点；
2. 解释为什么选择 X、Reddit、RSS、公开网页或其他合法来源；
3. 区分历史回填、增量采集和事件订阅；
4. 使用 Provider checkpoint、watermark、内容指纹和幂等键避免重复；
5. 规范化、聚类、排序并生成带引用的洞察；
6. 提供即时告警、定时简报、搜索和 Run / Evidence 视图；
7. 根据漏报、噪声、费用和用户反馈提出来源、频率、过滤器与分析方式的改进。

X 是首版必须验证的社交来源，但接入方式必须是官方 API、用户授权或合同明确的合规 Provider。RSS 和公开网页提供低成本基础覆盖；Reddit 等来源按价值、许可和实现成本逐步加入。Facebook、Instagram、Bluesky 等不在 MVP 做覆盖承诺。

这个场景验证的是通用闭环。同一模型未来可以支持技术变更跟踪、研究雷达、学习计划、竞争情报和重复数据分析。

## 价值指标

产品指标分为五组，不在没有真实基线前承诺虚假 SLA：

| 维度 | 关注指标 |
| --- | --- |
| 激活 | 从目标输入到首个可审查方案、首个有用结果的时间 |
| 结果质量 | 有用信号率、噪声率、漏报反馈、引用与证据覆盖率 |
| 运行质量 | 成功率、恢复率、重复率、积压、数据缺口和交付延迟 |
| 经济性 | 每个有用信号成本、模型与 Provider 成本、预算超限次数 |
| 治理 | 未授权动作、审批等待、版本回滚、退化检测和审计完整性 |

路线图阶段退出条件必须至少覆盖用户结果、可靠性、成本和治理四类证据。

## 非目标

- 不提供绕过登录、验证码、付费限制、速率限制或平台条款的数据抓取；
- 不把产品定位为免费获得所有社交平台数据的舆情 SaaS；
- 不以通用个人助理、操作系统控制、语音或消息渠道聚合为主线；
- 若 Pi 通过 Phase 0 Spike，不再叠加第二套 Agent Runtime；任何情况下都不把 Coding Agent 当通用工作流运行时；
- 不在 MVP 建设完整拖拽编排器、公共插件市场、复杂知识图谱或多层 Agent Teams；
- 不允许无人审核的生产工作流、Skill、Connector 或代码自修改；
- 不承诺模型结论天然正确，必须展示来源、覆盖缺口和不确定性。

## 当前状态

当前已完成：

- 产品定位、用户、核心模型、边界和首个场景的文档化；
- 系统架构、Pi 技术取舍、参考项目和 UI 设计体系的文档化；
- 中英文 README、Apache License 2.0 和知识库治理基线。

当前尚未实现：

- Web、API、CLI、身份、项目和设置界面；
- WorkflowSpec、编译器、Registry、Temporal Workflow 和 Worker；
- Pi Adapter、Connector SDK、Evidence、Evaluation 与 Evolution 机制；
- X、RSS、Web、Reddit、通知和如流 Adapter；
- 数据库、对象存储、秘密管理、可观测、CI 和部署配置。

实现状态变化必须依据代码、测试与真实运行证据更新，不能由计划或原型直接改写。
