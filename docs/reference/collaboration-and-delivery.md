# 协作与交付

## 基本工作方式

- 对话语言跟随用户语言，知识库正文统一使用中文。
- 开始修改前先读根 `CLAUDE.md`、`docs/CLAUDE.md` 和任务相关事实源。
- 先检查 Git 状态、当前分支、已有修改和真实文件结构，不基于旧对话或历史计划直接行动。
- 事实来自当前代码、测试、配置、授权数据源或可重复验证；无法确认时明确写“未验证”。
- 优先使用已有接口、类型、组件、工具和约定；不为当前任务进行无关重构。
- 变更应保持最小且完整：解决明确问题，同时补齐与该问题直接相关的错误处理、测试和文档。
- 外部评审、Issue 和用户描述是输入，不是自动成立的结论；先读代码或复现，再决定修改。

## 任务边界

开始工作时明确：

1. 目标结果是什么；
2. 哪些仓库、目录、数据源和外部系统在范围内；
3. 哪些行为只允许读取，哪些行为允许修改；
4. 哪些判断已被确认，哪些仍是假设；
5. 完成需要哪些验证证据。

如果完成任务需要扩大到新的仓库、生产环境、用户数据或不可逆外部动作，应先说明原因和影响，再取得明确授权。

## 用户修改保护

- 工作区中的已有修改默认属于用户，除非有证据证明它们由当前任务创建。
- 不使用会覆盖工作区的破坏性命令，不擅自回退、清理或格式化无关文件。
- 工作区包含混合修改时，只暂存当前任务的明确文件路径，不默认使用 `git add -A`。
- 需要移动或删除文档时，先搜索引用并确认有效事实已经迁移。
- 发现修改冲突时停止覆盖动作，保留证据并向用户说明具体冲突。

## 设计与实施

- 新功能和行为变更先形成设计，明确产品边界、组件职责、数据流、错误处理、安全和验证方式。
- 未确认设计进入 `docs/plans`，不能提前写入 `docs/design/features`。
- 实施计划使用准确文件路径、接口、步骤和预期验证结果，不使用空白占位。
- 实现应达到可上线标准，但不预先建设没有当前需求的扩展点。
- Coding Agent 可以生成模块，但不能绕过工程评审、测试、秘密管理、沙箱或发布控制。

## 文档回写

- 设计与实施过程记录放在 `docs/plans`。
- 已采纳的跨功能长期设计回写到 `docs/design/core`。
- 已经落地的功能事实回写到 `docs/design/features`。
- 跨任务复用的工程规则回写到 `docs/reference`。
- 原型放在 `docs/prototype`，并显著声明不是实现事实源。
- 完成计划在事实回写和引用更新后删除，历史通过 Git、Issue 或 PR 查询。

## Git 与外部操作

- AI Agent 未经用户明确授权不得执行 `git commit`、`git push`、`git tag` 或创建发布。
- 获得提交授权后，先检查完整差异和暂存范围，提交信息应准确描述本次变更。
- 默认通过评审分支或 PR 交付；只有用户明确要求直推且仓库策略允许时才直接推送默认分支。
- 推送后必须回读远端分支、提交和关键文件；本地成功不等于远端已经生效。
- 发送消息、修改账号、触发付费任务、发布内容或操作第三方平台前，确认目标、成本和可逆性。

## 交付要求

最终说明至少包含：

- 实际完成的结果；
- 主要文件或模块；
- 实际运行的验证及结论；
- 未运行的检查及原因；
- 尚未实现、未验证或仍受外部条件限制的内容；
- 提交、分支、PR 或远端回读结果（如果本次包含发布）。

不得把“代码已写”“命令未报错”或“理论上可行”单独作为功能完成证据。
